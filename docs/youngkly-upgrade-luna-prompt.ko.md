7. 원본 보고서와 기존 결과물을 덮어쓰지 않는다. 검증 결과물은 별도 폴더에 생성한다. 서버에서 계산을 제출하거나 원격 파일을 수정하지 않는다.

## 1. 파일을 읽어오는 속도 개선

현재 `resolveFiles()`는 요청 파일명을 서버별 find에 묶어 찾지만, 발견한 파일은 파일별 SSH cat으로 내려받는다. 이미 있는 일괄 검색을 새 개선으로 보고하지 마라. 로컬 캐시 파일이 존재한다는 이유만으로 최신 데이터라고 판단해서도 안 된다.

### 구현

1. 먼저 단계를 구분해 시간을 계측하라: 시트 다운로드, XLSX 해석, 원격 검색, 원격 메타데이터 확인, 다운로드, Gaussian 분석. 렌더링과 DOCX 생성은 별도 집계한다. 로그에 파일 수, 전송 바이트, 캐시 적중 수, SSH 실행 횟수를 남긴다. 키 내용이나 인증 정보는 기록하지 않는다.
2. 동일 spreadsheet ID는 한 번의 실행에서 한 번만 내려받고 여러 탭이 공유하게 한다. 기존 구현에서 이미 수행 중이면 유지하고 검증만 한다.
3. 서버·정규화된 원격 경로·파일 메타데이터를 포함하는 캐시 manifest를 만든다. 변경되지 않은 파일은 재다운로드하지 않는다. 최소 size/mtime을 확인하며, 이를 완전한 내용 동일성 증명이라고 표현하지 않는다. 강제 새로고침은 재다운로드·SHA-256 갱신을 수행한다.
4. 원격 메타데이터는 가능한 한 서버별로 묶어서 조회한다. 다운로드는 기본 최대 3개로 제한된 동시 실행을 사용한다. 서버 우선순위에 따른 경로 확정은 기존 의미대로 수행한 후 전송을 병렬화한다. 동시 완료 순서로 보고서 순서가 바뀌지 않게 한다.
5. 임시 파일로 받은 후 검증에 성공한 파일만 원자적으로 캐시에 반영한다. 전송 도중 원본이 바뀌거나 중단된 경우 완료 캐시로 취급하지 않는다. 재시도는 횟수를 제한한다.
6. 파싱 결과도 재사용한다. 키에 원본 및 BB 내용 해시, parser/schema 버전, 파싱에 영향을 주는 설정을 포함한다. 문장 템플릿과 표시 설정을 바꿨을 때 이전 문장이 남지 않도록 원시 분석 캐시와 보고서 생성 결과를 구분한다.
7. 파일 위치 캐시를 추가할 경우 상위 서버의 신규 동명 파일이나 같은 서버의 중복 파일을 가리지 않게 한다. 경로 캐시만 믿고 서버 우선순위와 중복 검출을 생략하는 최적화는 금지한다.
8. UI 스레드에서 긴 작업을 기다리지 않게 한다. 실제로 실행 중인 단계와 완료 개수를 보여 주고, 오류와 취소를 처리한다. 기존 `-Offline`의 '시트 다운로드만 생략' 의미는 유지한다.

### 검증

- 같은 데이터로 최초 실행과 캐시 재실행을 분리하여 전후 시간을 비교한다. 파일 수·총 용량·캐시 상태·측정 횟수와 중앙값을 함께 기록한다.
- 변경 없는 재실행은 원격 출력 파일 본문 다운로드 0회, Gaussian 재파싱 0회여야 한다. 메타데이터 확인은 허용한다.
- 한 파일만 바꾸면 해당 파일과 그에 의존하는 분석만 갱신되어야 한다. BB 변경도 반영되어야 한다.
- 서버 실패, 중복 경로, 중단 전송, 공백·한글 경로, 서로 다른 연구의 동명 파일을 검증한다.
- 속도 배수를 미리 약속하지 말고 실측치를 보고한다. 서버에 연결할 수 없다면 로컬 fixture 측정과 원격 미검증 범위를 구분한다.

## 2. RC·TS·PC를 같은 뷰로 출력

'같은 뷰'는 카메라 회전만 복사한다는 뜻이 아니다. 서로 다른 좌표계에 저장된 구조를 공통 골격으로 정렬하고, 같은 방향·투영·크기 기준·여백으로 비교할 수 있어야 한다.

### 구현

1. 뷰 선택의 단위를 개별 구조에서 하나의 RC–TS–PC 그룹으로 바꾼다. 세 구조를 함께 확인하며 하나의 뷰를 조절하고 그룹 전체에 적용한다.
2. 기본 정렬 기준은 TS다. 사용자 지정 anchor atom IDs가 있으면 우선 사용한다. 없으면 검증된 원자 대응과 공통 중원자 골격으로 정렬 후보를 만들고 사용자가 확인할 수 있게 한다. 동일 원소 순서만으로 동일 원자 대응이 검증됐다고 주장하지 않는다.
3. 검증된 대응 원자에 대해 병진 및 proper rotation만 허용하는 강체 정렬을 수행한다. 반사·비균일 확대·좌표 변형은 금지한다. Kabsch 등의 회전은 det(R)=+1을 보장한다. 원자 수 불일치, 대응 불명확, 유효 anchor 부족 또는 퇴화 배치는 조용히 통과시키지 말고 대응/anchor 지정이 필요한 상태로 남긴다.
4. 정렬은 시각화 좌표에만 적용한다. 에너지·거리·각·spin 분석의 원본 좌표와 atom ID를 수정하지 않는다. TS 진동 변위 벡터에는 같은 회전을 적용하되 병진은 적용하지 않는다.
5. 카메라 orientation, projection, target, pan, zoom 및 Å당 픽셀 비율을 그룹에서 공유한다. 가능하면 기존 renderer API를 확장하여 직렬화 가능한 view state를 사용한다. 마우스 이벤트 재생을 카메라 저장 방식으로 사용하지 않는다.
6. 정렬된 세 구조와 TS 전체 진동 프레임의 투영 범위를 합쳐 하나의 canvas/crop 범위를 산출한다. 구조마다 독립적으로 fit/crop하여 분자 크기가 달라지는 동작을 제거한다. PNG와 GIF의 해상도가 달라도 같은 정규화된 범위와 구도를 사용한다.
7. 배경, 원자·결합 크기, 조명, 그림자, 수소 표시와 C–H activation 예외도 그룹 전체에 적용한다. 기존 고해상도 출력 품질을 낮추지 않는다.
8. 그룹별 view state, 정렬 기준과 atom mapping, 입력 구조 해시를 저장한다. 입력·mapping이 달라지면 저장된 상태를 무조건 적용하지 않는다. '그룹 뷰 초기화'와 '그룹 전체 적용'을 제공한다.
9. RC/PC 역할은 검증된 경로 의미를 사용한다. IRC reverse를 무조건 RC, forward를 무조건 PC라고 간주하지 않는다. 의미가 불명확하면 원래 라벨과 순서를 유지하고 확인 대상으로 남긴다.

### 검증

- 같은 분자를 임의 회전·이동한 fixture는 정렬 후 공통 원자가 겹쳐야 한다.
- RC·TS·PC 사이에 같은 길이가 같은 픽셀 길이로 출력되어야 한다.
- TS GIF 전 프레임에서 잘림·구도 흔들림이 없어야 한다.
- 실제 샘플의 세 PNG와 GIF를 시각적으로 확인한다. 계산 데이터가 정렬 전후 동일한지도 검증한다.

## 3. 출판 논문에 가까운 표와 문단 배치

요구는 보고서의 조판 개선이다. 논문처럼 보이도록 새로운 연구 내용이나 수치를 추가하는 것이 아니다. 표에 없는 항목을 자동으로 표에 끼워 넣지 말고, 기존 본문 내용도 임의로 표에 편입하거나 삭제하지 마라.

### 구현 기본값

- 절제된 3선 표를 사용한다. 위·아래 선 0.75 pt, 헤더 아래 선 0.5 pt, 세로선·모든 셀 격자·장식 배경색은 사용하지 않는다. 현행에도 3선 표가 있으므로 실제 개선은 간격·열 폭·가독성·페이지 흐름에 집중한다.
- 표 내부 문단 앞/뒤 0 pt, 줄간격 1.0, 셀 상하 여백 3 pt, 좌우 여백 4 pt를 기본값으로 둔다.
- 표와 인접 본문 사이 8 pt, 연속된 표 사이 12 pt를 기본값으로 둔다. 빈 문단 여러 개를 쌓아 간격을 만들지 않는다. Word에서 필요한 구분 문단은 하나만 두고 높이와 간격을 명시한다.
- 본문은 원본의 폰트·크기를 우선 유지한다. 표는 9 pt를 기본으로 하되 폭이 넓은 에너지 표는 현행 최소 8 pt까지 허용한다. 공간을 맞추기 위해 더 작게 축소하지 않는다.
- 열 폭은 무조건 균등 분배하지 않는다. 긴 원자/geometry 라벨 열과 수치 열을 구분해 실제 페이지 유효 폭에 맞춘다. 표 숫자의 자릿수와 정렬을 일관되게 유지한다.
- 값의 반올림 자리, SI 열 순서, `E Total`·`ΔG` 강조, 단위와 위/아래첨자를 유지한다. 새로운 통계·오차·유의성·각주 내용을 만들어 넣지 않는다.
- 헤더 행 반복과 개별 행 분할 금지를 적용한다. 표 전체 모든 행에 keepNext를 연쇄 적용해서 큰 공백이나 빈 페이지를 만들지 않는다. 제목·기존 캡션이 표와 떨어지지 않게 한다.
- 긴 표는 페이지를 넘길 수 있어야 한다. 모든 표를 억지로 한 페이지에 넣지 않는다. Future work는 새 페이지에서 시작한다.
- 위 값은 한곳의 layout 설정으로 관리한다. 실제 렌더링에서 필요한 소폭 조정은 허용하되 최종 값을 문서화한다.

### 검증

- 조판 수정만 적용한 전후 DOCX에서 표의 셀 값·행·열·단위가 동일한지 비교한다. 별도의 명시적 오류 수정이 있으면 따로 설명한다.
- Word 또는 사용 가능한 문서 렌더러로 전체 페이지를 렌더링하고 확인한다. XML 검사만으로 시각 검증을 대신하지 않는다.
- 헤더 줄바꿈, 숫자 잘림, 과도한 공백, 제목 고립, 표 행 분할, 페이지 밖 넘침이 없어야 한다.
- 렌더러를 사용할 수 없으면 검증 완료라고 쓰지 말고 구조 검증 결과와 시각 검증 미완료를 구분한다.

## 4. Spin density와 key geometry 문장 템플릿 확장

### 사용자의 문체를 추출하는 기준

원본 DOCX의 본문과 Future work를 직접 읽어라. 다음은 문체의 특징이지 모든 문장에 강제할 양식이 아니다.

- 한국어 서술 안에 transition state, energy barrier, intermediate, coordination 등 익숙한 연구 용어를 자연스럽게 쓴다.
- 연구 맥락을 짧게 설명하고 수치나 구조 변화를 말한 뒤, 근거가 있는 경우에만 해석이나 다음 계산으로 이어간다.
- '나타났으며', '확인하였습니다', '계산을 진행하고자 합니다', '확인해 보고자 합니다' 등의 종결을 맥락에 따라 사용한다.
- 모든 행을 하나씩 읽는 보고 문장을 반복하거나, 모든 문장을 '이는 …을 시사합니다'로 끝내지 않는다.
- '유의미한 통찰', '종합적으로 고려할 때', '명확하게 입증합니다', '중요한 의미를 가집니다' 같은 내용 없는 문구를 넣지 않는다.
- 원본에 직접적인 spin density/각도 문장 사례가 부족하면 '사용자 문체에 맞춘 신규 초안'으로 개발 문서에 표시한다. 확정된 사용자 표현이라고 주장하지 않는다.

### 공통 구현

1. 수치 관측, 변화 유형 분류, 문장 조합을 분리한다. 템플릿은 `config/phrases.ko.json` 또는 이에 준하는 버전 관리 가능한 설정으로 관리한다.
2. 문장에는 표에 표시된 동일한 atom ID·수치·단위를 사용한다. 내부 원시 정밀도로 변화 유형을 판정하되 표시 반올림과 모순되는 문장을 만들지 않는다. `-0.000`은 `0.000`으로 정규화한다.
3. 각 문장이 참조한 표·행·원자·원시 수치·규칙을 report model에 남겨 추적 가능하게 한다. 기존 DOCX의 template_key 분기 역시 함께 갱신하여 새 문장이 누락되거나 잘못된 표 아래에 배치되지 않게 한다.
4. 같은 입력에는 같은 문장이 나오게 한다. 표현을 다양화하려고 무작위 동의어를 선택하지 않는다. 변화 유형과 문맥에 따라 문장을 선택하고 중복 정보를 합친다.
5. 표를 채우거나 문장을 늘리기 위해 분석 대상을 추가하지 않는다. 금속과 검증된 반응 중심부터 다루고, 이미 설명한 변화의 단순 반복은 생략한다. 중요 변화가 많으면 누락 없이 별도 문장으로 다룬다.
6. 관측 사실 문장은 자동 생성할 수 있다. 산화 상태 변화·전자 이동·radical 생성·결합 형성/절단 같은 해석은 검증된 추가 근거나 명시적인 사용자 해석이 있을 때만 쓴다. spin 값이나 거리 임계값 하나로 결론을 확정하지 않는다.
7. 누락값과 대응 불명확은 유지·0·변화 없음으로 서술하지 않는다. 필요한 검토 사유는 모델/검토 UI에 남긴다. `이는 ~~`, `{atom}` 같은 미완성 문자열을 최종 DOCX에 출력하지 않는다.

### Spin density 변화 유형

최소한 단조 증가, 단조 감소, TS에서만 증가, TS에서만 감소, 부호 전환, 변화 작음, 표시 정밀도 내 동일, 데이터 불충분을 구분한다. 부호 전환과 크기 증감은 별도 속성으로 취급한다. 0 부근의 수치 잡음은 부호 전환으로 과장하지 않는다.

기존 `spin_change_threshold`는 검토 후보 선택 기준이지 통계적 유의성이나 물리적 상태 판정 기준이 아니다. '유의미한 변화'라는 표현을 임계값만으로 생성하지 않는다. ligand/group 합계는 해당 구성 원자의 데이터가 모두 존재할 때만 계산하고 원자별 값과 혼동하지 않는다.

다음은 문장 형태 예시이며 실제 값은 반드시 입력에서 가져온다.

- 단조 변화: `{atom}의 spin density는 RC에서 {rc}, TS에서 {ts}, PC에서 {pc}로 감소하였습니다.`
- TS 국소 변화: `{atom}의 spin density는 TS에서 {ts}까지 증가하였으나, PC에서는 {pc}로 다시 감소하였습니다.`
- 부호 전환: `{atom}의 spin density는 RC에서 {rc}였으며, PC에서는 {pc}로 부호가 바뀌었습니다.`
- 작은 변화: `{atom}의 spin density는 {min}–{max} 범위로, 세 구조 사이의 변화는 크지 않았습니다.`
- 표시 정밀도 내 동일: `{atom}의 spin density는 세 구조에서 모두 {value}로 나타났습니다.`

위 예시는 출발점이다. 실제 원본 문체에 맞춰 최종 템플릿을 다듬고, 모든 원자에 똑같은 문장 구조를 반복하지 마라. 검증되지 않은 RC/PC 역할은 실제 구조 라벨로 대체한다.

### Key geometry 변화 유형

거리 감소·증가, TS에서만 변하는 거리, 각도 증가·감소, 이면각 변화, 변화 작음, 데이터 불충분을 구분한다.

- 거리 단위는 Å, 각도·이면각은 °다. 각도 행을 거리 문장으로 출력하지 않는다.
- 이면각은 주기성을 고려한다. 예를 들어 +179° → −179°를 358° 변화로 서술하지 않는다. 세 상태를 일관된 branch로 unwrap하여 변화 유형을 판정하고 표의 표시 값은 보존한다.
- 기본 거리 변화 기준 0.15 Å, 각도 기준 5°는 후보 선정 기준으로만 사용한다. 임의의 거리 cutoff로 화학 결합 형성·절단을 확정하지 않는다.
- 사용자 지정 `geometry_atom_groups`를 우선 사용한다. 자동 검출 후보는 원자 대응과 항목 선택의 검토 상태를 보존한다.

문장 형태 예시:

- `{a}–{b} 거리는 RC에서 {rc} Å였으며, TS에서 {ts} Å를 거쳐 PC에서 {pc} Å까지 짧아졌습니다.`
- `{a}–{b}–{c} 각도는 {rc}°에서 {pc}°로 증가하였습니다.`
- `{a}–{b} 거리는 TS에서 {ts} Å로 길어졌으나, PC에서는 {pc} Å로 다시 짧아졌습니다.`

부호와 정밀도 경계, 0, 누락, 비단조 변화, ±180° 이면각, 다중 금속, 검증되지 않은 atom mapping을 fixture로 검증하라. 수치·단위·문장 방향이 표와 일치해야 한다.

## 5. Future work를 연구 계획으로 구현

Future work는 미완료 파일 목록이나 사용자에게 '작성해주세요'라고 요청하는 공간이 아니다. 이번 결과·미해결 문제·협의 내용으로부터 다음에 무엇을 왜 확인할지를 적는 부분이다. 다만 근거가 없는 다음 계산을 자동으로 발명해서는 안 된다.

원본에는 결과에 따른 후속 경로 검토, 높은 barrier의 개선 가능성 검토, 비교 계산, 공동연구자와의 논의 및 발표 자료 준비가 포함되어 있다. 이는 가능한 항목 종류의 예시다. 이전 주에 적힌 과제·일정·논의가 이번 주에도 유효하다고 추정하지 마라.

### 구현

1. 기존 `kind == in_progress` 행만 반복 출력하는 방식과 `{filename}에 대한 … 작성해주세요` 문구를 교체한다.
2. 보고 날짜·연구·세부 주제에 연결된 구조화된 입력을 추가한다. 최소 필드는 연구 ID, 주제, 근거/출처, 현재 확인된 결과, 미해결 질문, 다음 행동, 그 목적, 진행 상태, 선택적 일정, 확인 여부다. 필드를 채우기 위해 없는 내용을 만들지 않는다.
3. 기존 앱 안에서 이 항목을 입력·수정·보존할 수 있는 최소한의 편집 경로를 제공한다. 서버에 연결하지 않고도 연구 계획을 수정할 수 있어야 한다. 기존 보고서 생성 흐름과 선택된 보고 날짜에 연결한다.
4. 확정 계획과 제안을 구분한다. 사용자가 입력한 계획 또는 명시적 현행 자료로 확인된 계획만 확정 문장으로 출력한다. 자동 제안은 검토 UI에 남기고 확인되기 전에는 '진행 중', '수행할 계획'으로 쓰지 않는다.
5. 입력 파일 존재만으로 계산 진행 중이라고 쓰지 않는다. 출력이 없다는 이유만으로 실패·대기·진행 중 중 하나를 임의 판정하지 않는다. 상태를 확인할 근거가 없으면 내부적으로 unknown으로 둔다.
6. 완료된 계산에서도 명시적 후속 계획이 있으면 Future work에 포함할 수 있어야 한다. 반대로 미완료 파일이 있어도 연구 계획을 알 수 없다면 계획을 꾸며 넣지 않는다.
7. 같은 연구 질문의 여러 파일을 한 항목으로 묶는다. 서로 다른 연구·반응·목적을 파일명이 유사하다는 이유로 합치지 않는다.
8. 연구 → 세부 주제 순으로 원본과 같은 자연스러운 문단을 만든다. 가능한 경우 '현재 결과/문제 → 확인할 내용과 목적 → 다음 행동' 순서로 연결하되 모든 문단에 세 요소를 억지로 채우지 않는다.
9. 다음 주·진행 중·완료 등 시간과 상태는 선택된 보고 날짜에 맞는 근거가 있을 때만 사용한다. 과거 항목은 이월 후보로 표시하고 자동으로 날짜를 바꾸거나 재확정하지 않는다.
10. 자료가 없으면 내부 검토 목록에 '계획 입력 필요'로 남긴다. 최종 보고서에는 작성 지시, 빈칸 안내, 가짜 계획을 넣지 않는다. Future work 제목과 새 페이지 시작은 유지할 수 있지만 내용 부재를 완료된 계획처럼 포장하지 않는다.

문체 예시: `이번 계산에서는 {확인된 결과}를 확인하였습니다. 다만 {확인된 미해결 문제}가 있어, 다음 단계에서는 {명시된 계산/검토}를 통해 {목적}을 확인해 보고자 합니다.`

이 예시를 모든 항목에 반복 적용하지 마라. 완료 사실, 문제, 다음 행동 중 하나라도 근거가 없으면 해당 절을 생략한다. 계획만 제공된 경우에는 계획만 자연스럽게 서술한다.

### 검증

- 입력 파일만 있는 경우 계산 진행 중이라고 단정하지 않는다.
- 완료 결과에 연결된 사용자 계획을 출력할 수 있다.
- 이전 주 계획을 이번 주 사실로 자동 복사하지 않는다.
- 사용자 계획 수정·삭제·다시 열기가 보존된다.
- 자동 제안이 확인 없이 최종 보고서에 들어가지 않는다.
- 계획 자료가 없는 경우 가짜 문장이나 placeholder가 나오지 않는다.

## 6. 구현 순서와 완료 보고

다음 순서로 진행하라.

1. 현재 동작·실제 병목·기존 변경을 확인하고 기준 결과와 시간을 보존한다.
2. 파일 로딩 계측과 캐시/전송 개선을 구현한다.
3. 그룹 구조 정렬·공유 카메라·공통 crop을 구현한다.
4. 문장 규칙과 Future work 데이터/편집 흐름을 구현한다.
5. 표와 문단 조판을 개선한다.
6. 기존 테스트와 위 요구에 필요한 회귀 테스트를 실행한다. 실제 fixture로 보고서를 생성하고 그림·GIF·문서 전체 페이지를 확인한다.
7. README와 설정 설명을 최종 동작에 맞춰 갱신한다. 기존 사용자 설정에 신규 기본값을 호환 방식으로 적용하고 입력한 문장/계획을 덮어쓰지 않는다.
8. 빌드·패키징이 가능하면 별도 검증 폴더에 배포 EXE를 만들고 실행을 확인한다. 사용자 실행 파일을 확인 없이 교체하지 않는다. 외부 SI/Youngcraft 의존성을 수정했다면 수정 경로와 영향도 명시한다.

최종 보고에는 아래만 명확하게 적어라.

- 다섯 요구별 실제 구현 내용과 변경 파일
- 최초 실행/재실행 성능 측정값과 측정 조건
- 같은 뷰의 PNG·GIF 검증 결과
- 조판 전후 비교 결과와 최종 보고서 경로
- 실제 수치가 들어간 spin/geometry 문장 예시 및 근거가 확인된 Future work 예시
- 실행한 테스트, 실패 또는 미검증 항목, 남은 제약

구현하지 않은 것을 구현했다고 쓰지 마라. 테스트만 통과하고 실제 보고서의 문장·그림·페이지를 확인하지 않은 상태를 전체 검증 완료로 보고하지 마라. 환경 때문에 검증이 막히더라도 독립적으로 가능한 구현과 검증은 마무리하고, 필요한 사용자 조치는 구체적으로 설명하라.
